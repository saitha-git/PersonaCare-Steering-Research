Activation Steering on the Edge

A measured proof of concept: extract a steering vector from contrast pairs, inject it into a small LLM's residual stream with a live dose dial, prove the behavior change statistically, express the intervention as a two-op ONNX graph — and run that graph 100% NPU-resident on Snapdragon X Elite silicon.

Method

One vector, one dial

The behavioral concept is verbosity (benign, easy to score: response length). 24 content-matched sentence pairs — same fact, one verbose phrasing, one concise — live in data/contrast_pairs.jsonl; a deterministic 20% holdout never touches extraction.

steered = hidden + α · mask · v   hidden [B,T,D] · v [1,1,D] · α [1] · mask [B,T,1]

Extract. Both members of each pair run through the model with capture hooks on the output of decoder layer i — the residual stream after that layer's attention, MLP, and both residual adds — at the last non-padding token. The vector is mean(act(verbose) − act(concise)), saved with model revision, dataset SHA-256, capture point, and holdout indices.

Inject. A forward hook replaces the layer output with the steered tensor — out-of-place, KV-cache-safe, preserving tuple outputs. Under generate(), prefill sees [B,T,D] and each cached decode step sees [B,1,D]; both are steered. Hooks install and remove via an exception-safe context manager.

Control. α is the dose: negative → concise, positive → verbose, and α = 0 reproduces the un-hooked model bit-exactly (measured max deviation 0.00e+00 across all layers and 32 prompts).

Experiments · Milestone A

Behavior follows the dial

Sweep: layers {7, 14, 21} × α {−4…+4}, 32 diverse prompts, greedy decoding, max_new_tokens=512. Evaluation is censoring-aware: every generation records token IDs, reached_eos, and hit_max_new_tokens; the 0–3 generations per cell that hit the cap are excluded from word statistics — a truncated answer is never counted as short.

Paired Δwords vs α = 0 per prompt, mean with 95% percentile bootstrap CI (10k resamples), uncensored pairs only.

Layer 7's CIs exclude zero at α = −4, −2, and +4 against a 147-word uncensored baseline. Layers 14 and 21 are weak-to-null at unit vector norm — late-layer residual magnitudes dwarf a unit vector (raw difference norms grow 8 → 175 from layer 3 to 25). Reported as measured, not cherry-picked. Fluency holds: NLL of steered text under the unsteered model stays 0.38–0.42 nats/token at every dose, and KL from baseline scales smoothly (0 → 0.0015 → 0.03 for α = 0 → ±1 → ±4).

Experiments · Milestone B

The whole intervention is Mul + Add

The op exports to ONNX (opset 17) as exactly two node types with v, α, and mask as runtime inputs — no recompilation to change dose or direction. Three graphs ship: prefill [1,16,1024], decode [1,1,1024], and dynamic-T (fixed shapes exist because HTP compilation prefers them). One deployment-driven detail: α is rank-1 [1], not a scalar — AI Hub's uploader can't ship rank-0 tensors while the compiled QNN graph enforces ranks exactly.

Experiments · Split compute

One LLM, two Snapdragons

Follow-up experiment (separate package, src/split_compute/): can decoder layers 0–13 of Qwen3-0.6B run on a phone NPU and layers 14–27 on a laptop NPU, with the residual hidden state as the only tensor crossing devices? This mirrors Qualcomm's own multi-split LLM packaging, where the hidden state is already a boundary graph I/O. The split is a fixed-shape prompt-processor graph (T=32, no KV cache); the boundary payload is 2 KB per token at fp16.

Local gate first (free): the ONNX PartA→PartB chain matches the full fp32 model to max logit diff 7.9e-5, 100% argmax agreement. Then on real silicon — PartA compiled for and run on a Snapdragon 8 Elite QRD (phone), its output activations downloaded and fed to PartB on a Snapdragon X Elite CRD (laptop):

100%greedy argmax agreement with local fp32, all 32 positions — the two-device pipeline predicts identical tokens
fp16-exactboundary crossing: max err 4.16 on a 6,520-magnitude outlier channel = 6.4e-4 relative
829 + 832 ops NPUevery op of both halves on the Hexagon NPU of its device
6.1 + 16.4 ms32-token prefill compute: phone half + laptop half (LM head dominates part B)

Chained logits vs local single-device fp32: max abs diff 0.120, mean 6.4e-3, KL(last position) 2.1e-5. Job record: artifacts/split/ai_hub_split_jobs.json. What this does not show: AI Hub has no device-to-device transport, so the cloud round trip stood in for the network — live transport latency, streaming KV-cached decode, and power remain unmeasured. A real-time pipeline adds roughly network RTT per generated token on top of the two compute halves.

Findings

What we claim — and what we don't

Demonstrated

  • Statistically defensible dose-response at layer 7 (CIs exclude zero; ρ = +0.25)
  • α = 0 is a bit-exact identity; hooks are exception-safe and leave the model pristine
  • ONNX parity bit-exact on ORT CPU; signal survives FP16, INT8, and a real QDQ INT8 graph
  • Compiled, linked, executed, and profiled on Snapdragon X Elite — 100% NPU, fp16-exact
  • Pipeline-split Qwen3-0.6B across a phone NPU and a laptop NPU with 100% greedy-token agreement (functional verification via chained AI Hub jobs)
  • Qualcomm reality check from source: AI Hub's Qwen3-0.6B ships only as GGUF Q4_0 under llama.cpp (GenieX) — catalog presence ≠ editable QNN graph. Editable recipes start at Llama-3.2-1B / Qwen3-1.7B, where the residual stream crosses split boundaries as graph I/O

Not yet

  • Steering inside Qualcomm's deployed LLM (Genie/GenieX) — requires patching the qai-hub-models export and recompiling the affected split; exact patch points in docs/qualcomm_integration_plan.md
  • CPU split-boundary intervention — proposed, unverified (raw-QNN orchestration loop and uint16 activation re-encoding unproven)
  • Full-LLM Snapdragon latency/power — the 180 µs figure is the standalone op only
  • Live cross-device transport & streaming decode for the split pipeline — the cloud round trip replaced the real network; a live demo needs an orchestrator + socket on both devices and KV-cached per-part graphs

Runbook

Running it on a real Snapdragon machine

Path 1 — Real Snapdragon silicon via AI Hub Workbench (verified; no hardware owned)

  1. Get a (free) API token from workbench.aihub.qualcomm.com/account and configure it once: qai-hub configure --api_token <token>. Never commit it.
  2. Export the graphs: python -m steering_poc.export_onnx --hidden-size 1024
  3. Dry-run first (prints the plan, submits nothing): python -m steering_poc.qualcomm.submit_ai_hub
  4. Submit for real: python -m steering_poc.qualcomm.submit_ai_hub --submit --infer --profile --device "Snapdragon X Elite". The script resolves the device from the live list, compiles ONNX → qnn_dlc, links to a QNN context binary, runs on-device inference (compared to local ORT at the fp16-appropriate tol 1e-2), profiles, and writes job URLs to artifacts/ai_hub_jobs.json.
  5. Optional: --multi-graph links prefill + decode as two graphs of one weight-shared context binary — the same packaging Qualcomm uses for LLM prompt/token graphs.

Path 2 — On a Snapdragon X Elite laptop you're holding (Windows-on-ARM)

  1. Install ARM64 Python, then pip install onnxruntime-qnn (ships the QNN Execution Provider + Hexagon backend DLLs).
  2. Run the graph on the NPU with CPU fallback disabled so unsupported ops fail loudly instead of silently running on CPU — python -m steering_poc.qualcomm.qnn_emulation --model artifacts/steering_injection_prefill.onnx does exactly this:
so = ort.SessionOptions()
so.add_session_config_entry("session.disable_cpu_ep_fallback", "1")
sess = ort.InferenceSession("steering_injection_prefill.onnx", sess_options=so,
                            providers=["QNNExecutionProvider"],
                            provider_options=[{"backend_path": "QnnHtp.dll"}])
  1. Alternatively, download the compiled context binary from the AI Hub link job (jp2vd2wm5) and run it with the QAIRT SDK: qnn-net-run --retrieve_context <binary> --backend QnnHtp.dll --input_list ... (a DLC/context binary is not a directly executable model — --retrieve_context is the correct entry point).

Path 3 — Steering inside the full on-device LLM (the integration milestone)

This is engineering, not a command. The plan in docs/qualcomm_integration_plan.md is grounded in Qualcomm's actual source: patch the steering Add into the qai-hub-models monkey-patch layer for Llama-3.2-1B (or Qwen3-1.7B+), inside a decoder layer rather than between layers — split_onnx counts residual Adds to find split boundaries, and a bare extra Add can silently shift them — then recompile the one affected split and reassemble the Genie bundle. Recommended graph form for a hackathon: hidden + Σ coeffᵢ · vᵢ with K compiled vectors and a small runtime coefficient input.

Honesty note. Desktop emulation and cloud CRDs validate graph acceptance and functional numerics. They do not validate thermals, power, scheduling under load, or full-LLM latency. Nothing on this page claims otherwise.
